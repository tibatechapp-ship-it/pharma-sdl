# ADR-0007 — مهام دائمة + طريق الترقية إلى PostgreSQL/Celery/Redis

**الحالة:** مقبول (يُرقّي ADR-0005 جزئياً) · **التاريخ:** 2026-11-01 · **السياق:** تقييم ما قبل P2 (إشكاليات #2 و#3 و#7)

## السياق

ADR-0005 اختار طابور in-memory لصغر الحجم — صحيح حينها. لكن تقييم ما قبل P2
كشف التفاوت: السجل التجريبي صار دائماً (SQLite)، بينما المهام والنتائج تضيع
عند إعادة التشغيل، و`ValidationCard` (التاريخ والمرفقات) لا تُحفظ أصلاً —
فالمنصة «دائمة» جزئياً، والجزء الناقص هو ما يلمسه المستخدم.

## القرار

**1) طابور دائم بنفس العقد** (`jobs/runner.py` → `SQLiteJobStore`):
SQLite (نمط السجل التجريبي نفسه: stdlib، WAL، خيط-آمن) خلف واجهة
`submit/get/result_of/list` **بدون أي تغيير** — المستدعون لا يعرفون الفرق:

- المكتمل يعاد بنتيجه (pydantic → `model_dump_json` + اسم الصنف، أو JSON صريح).
- ما كان running/pending لحظة السقوط → `failed` بسبب موثق
  `interrupted by service restart` — المقاطعة توثَّق لا تُخفى.
- تنظيف TTL يبقى (قراءة نظيفة فوق تخزين دائم).

**2) بطاقة الاعتماد مع التجربة** (`experiments/registry.py`):
حقل `validation_card` داخل payload التجربة (JSON — بلا تعديل مخطط)،
`attach_validation`/`save_validation_card` يحفظان البطاقة الكاملة، و
`validation_card_of` يقرأها أو يشتق UNVALIDATED صادقاً بلا تاريخ مُختلق.

**3) طريق الترقية الصادق إلى PostgreSQL/Celery/Redis** (بلا كود غير مُختبر):

- `deploy/postgres/schema.sql` — مخطط JSONB جاهز (experiments + jobs).
- `pharma-sdl export-experiments` / `import-experiments` — JSONL سطر لكل
  تجربة كاملة؛ الاستيراد يحفظ المعرّفات وسلاسل الأسلاف ويكون آمن إعادة المحاولة.
- Celery/Redis عند تعدد المستخدمين: استبدال محلي في `jobs/runner.py` —
  الواجهة نفسها. **متى؟** أول أى من: مستخدمون متعددون متزامنون، مهام > 10 دقائق،
  تعدد نسخ API خلف موازن أحمال.

## البدائل المرفوضة

- **PostgreSQL فوراً:** خدمة إضافية بلا مستخدم يبررها؛ SQLite/WAL يتجاوز
  احتياج مستخدم علمي واحد بأمرين من حيث الكتابة.
- **Celery الآن بلا بروكر:** كود dead لا يُختبر في CI — ادعاء بلا قياس،
  عكس عقد الصدق؛ البديل: واجهة محفوظة + وثيقة تشغيل جاهزة.
- **مخزن بطاقات منفصل عن التجارب:** بطاقة بلا تجربتها يوحي بترقية نتيجة
  حُذفت؛ الربط بالسجل واحد هو الأصدق.

## النتائج

- إعادة النشر لا تفقد جولة فرز متوسطة ولا نتيجة مكتملة.
- «لماذا رُقّيت هذه النتيجة؟» يُجاب من السجل — عبر CLI أو API.
- الترقية للخدمات الحقيقية تشغيلية (مخطط + تصدير + استيراد) لا نظرية.
- جناح redocking (RMSD ≤ 2.0 Å ضد بلورات RCSB) يحمي المحرك الفعلي من
  الانحراف الصامت — نتائجه الموثقة في docs/audit/redocking-results.json.
